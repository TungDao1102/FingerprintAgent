# 04-02 PLAN: MSI Installer + C# CustomAction DLL + GitHub Actions Release Workflow

## Goal

Build a production-grade MSI installer (WiX 3.x + DTF CustomAction DLL) that replaces PowerShell-only deployment for hospital IT. The MSI installs the service, the runtime config template, and the ProgramData seed; detects missing VC++ x86 with a clear Vietnamese error; starts the service and validates it via `/health` probe; rolls back cleanly on any failure. Builds run in GitHub Actions on tag push (no local MSI build script per D-02). Uninstaller preserves logs by default with a `REMOVE_LOGS=1` escape hatch (D-28/29).

## Scope

D-01 through D-12, D-18, D-19, D-28 through D-31, D-34, D-38, D-39, D-40.

Supports DEP-01 (package contents) and DEP-02/03 (install/uninstall scripts at scale) by replacing the per-machine PowerShell approach with a single artifact that scales to IT-managed hospital workstations.

**v1 Deviation from ROADMAP.md SC #2** (DOCUMENTED): ROADMAP.md Phase 4 Success Criterion #2 says "MSI cài đặt service, thư mục log, và VC++ redist x86 silently nếu thiếu" (installs VC++ redist silently if missing). This contradicts D-09 (CONTEXT.md locked decision): "Detect only — error message if missing (no bundling)". The plan correctly implements D-09 with Vietnamese error dialog + aka.ms/vs/17/release/vc_redist.x86.exe download URL. The ROADMAP.md SC #2 wording is stale and should be updated by the project owner in a separate commit. Phase 4 will be marked complete against D-09 (the locked decision), not against the stale ROADMAP wording.

## Decisions Carried Forward

From Phase 3 CONTEXT (D-17): "health check timer does NOT call Initialize() or Scan()". Plan 04-03 (auto-update) does its own /health probe before triggering msiexec — must NOT collide with the CustomAction's post-install /health probe. Sequencing: CustomAction runs synchronously inside MSI transaction (after service starts, before commit). Plan 04-03 runs asynchronously in service process.

From CONTEXT (D-32): all 5 PowerShell scripts (`Install-Service.ps1`, `Uninstall-Service.ps1`, `Service.ps1`, `Setup-VendorSdk.ps1`, `Test-Capture.ps1`) are PRESERVED unchanged. MSI is the production path; PS1 is dev/test fallback.

## Anti-Patterns (do not extend)

- Do NOT add a local `Build-Msi.ps1` script — D-02 says GitHub Actions only
- Do NOT sign the MSI — D-07 unsigned v1
- Do NOT bundle vendor SDK DLLs in the MSI — D-32a vendor drivers installed separately
- Do NOT use `<CustomAction>` for service registration — use `<ServiceInstall>` per D-19
- Do NOT use a Burn bootstrapper — D-09 reject bundling
- Do NOT use `<MajorUpgrade Schedule="afterInstallInitialize">` — that stops service first then copies files (more downtime). Use `afterInstallExecute` for smooth upgrade
- Do NOT add a custom EULA dialog — WixUI_Minimal is sufficient for v1
- Do NOT add a `<Property Id="ARPNOMODIFY" Value="1" />` — Modify verb is fine to leave enabled for v1 (institutional IT rarely uses it anyway)
- Do NOT add `RemoveFolder` for ProgramData\Logs without the REMOVE_LOGS condition — D-28 says preserve logs by default
- Do NOT add `<CustomAction>` scheduling for VC++ check AFTER file copy — fail-fast means check before any file system mutations
- Do NOT require admin elevation beyond what MSI already requires — installer already elevates; CustomActions run elevated
- Do NOT add telemetry or crash reporting from CustomActions — out of scope per CONTEXT deferred
