# 04-03 PLAN: Auto-Update Timer + UpdateCheckService

## Goal

Add an in-process auto-update Timer (D-13) that polls GitHub Releases for new versions, downloads the MSI to `%TEMP%`, and invokes `msiexec /qn` to self-upgrade. Default DISABLED via `config.json` `update.enabled = false` (D-14) — operator opts in for initial rollout / hotfix period. Auto-backoff increases check interval from 6h → 12h → 24h after 3 consecutive no-update checks (D-15); resets to base interval on detected release. On update failure, disable `update.enabled` in config.json, log Error, write EventLog (D-43) — service keeps running on old version.

## Scope

D-13, D-14, D-15, D-16, D-17, D-43, D-44.

Note: D-41 (pre-install toast), D-42 (10s delay), D-45 (silent default) are covered by the implementation but the toast itself is skipped per RESEARCH.md §5 — Windows Service under LocalSystem cannot send toasts; falls back to EventLog + log file.

## Decisions Carried Forward

From Phase 3 CONTEXT (D-17): "health check timer does NOT call Initialize() or Scan()". The new update Timer is INDEPENDENT — different cadence (hours vs 30s), different action (HTTP GET vs observe). Both timers coexist in FingerprintAgentService.

From CONTEXT (D-22): GitHub Releases API returns latest NON-prerelease, NON-draft release. Defense in depth: also filter by `prerelease: false` in JSON response.

  </read_first>

  <acceptance_criteria>
    - In `CheckForUpdateAsync` (or its callback wrapper), after the check completes:
      - If newer version found: `_noUpdateCount = 0` AND `Timer.Change(BASE_INTERVAL_HOURS, BASE_INTERVAL_HOURS)`
      - If no newer version (HTTP 200 but version <= current): increment `_noUpdateCount` under lock, compute next interval:
        - count=1: 6h
        - count=2: 12h
        - count>=3: 24h (capped)
        - `Timer.Change(nextInterval, nextInterval)` to apply new period
    - On HTTP error: also increment counter, same backoff progression
    - Log each interval change with current `_noUpdateCount` and next interval hours
    - Constants match the table:
      - `private static readonly int[] BackoffHours = { 6, 12, 24 }`
    - The cap at 24h means: even after 100 no-update checks, interval stays at 24h
  </acceptance_criteria>

  <description>
    Per D-15: when stable for a while, check less often. When a release is detected, snap back to base interval immediately.

    The Timer.Change() approach: pass `TimeSpan.FromHours(N)` for both dueTime and period. Since the Timer is already running, calling Change() resets the schedule without stopping/starting.

    Log example:
    ```
    UpdateCheck: no newer version, backoff step=2, next interval=12h
    UpdateCheck: new release detected (v1.2.4), backoff reset to 6h
    ```
  </description>
</task>

## Anti-Patterns (do not extend)

- Do NOT introduce DI container for UpdateCheckService (per AGENTS.md "No DI container")
- Do NOT use System.Text.Json (use Newtonsoft per project convention)
- Do NOT use TaskScheduler or Quartz.NET — plain System.Threading.Timer is sufficient
- Do NOT add `Microsoft.Toolkit.Uwp.Notifications` NuGet dep — toast will never work under LocalSystem; fall back to EventLog (per RESEARCH.md §5)
- Do NOT catch UnauthorizedAccessException for toast and crash — swallow silently, log Info
- Do NOT call ConfigLoader.Load() in failure path — partial JSON rewrite is sufficient and avoids re-running merge logic
- Do NOT add delta-update or rollback support — deferred to Phase 5+ per CONTEXT deferred
- Do NOT cache the old MSI for rollback — D-17 explicitly says no
- Do NOT add a "check for update" button to the UI — Programs and Features Update verb opens GitHub releases page per D-18, that's sufficient for v1
- Do NOT start the Timer if `update.enabled = false` AND there's no env var override — saves resource cost on default installations
